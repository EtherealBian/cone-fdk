# 同样的局部灰度，能唯一决定这里是不是孔吗？

**不能。** 在开发试件 2、3、5 的同一段 96 层里，把去噪后的中心、圆盘最低和最高 8 位灰度以及该件对比度完全相同的位置分成一组。每件都有一部分组同时含有参考孔与参考材料。只看这四个数、对相同输入必定给相同答案的算法，即使事先知道参考答案，也至少会判错下表中的体素数。这个下限仅适用于当前去噪和编码；原始 16 位 CT 及周围三维结构仍可能提供信息。

|试件（每件 6,291,456 体素）|观测组合数 / 孔与材料冲突的组合数|至少错判体素|知道本区域答案后的最高 Dice（精确分数）|只用校准标签的字典：实际 Dice|
|---|---:|---:|---|---:|
|[2](evidence/byte-window/sample2.json)|109,869 / 2,408|4,004|0.97140（4857/5000）|0.93631|
|[3](evidence/byte-window/sample3.json)|453,474 / 35,478|66,085|0.97256（260264/267607）|0.96497|
|[5](evidence/byte-window/sample5.json)|357,610 / 16,573|22,760|0.98411（140995/143271）|0.97431|

三个 Dice 上限都超过 0.95，因此**不能**据此宣称仅用这四个数一定过不了 Dice 门槛。上限也不约束逐孔体积：3 号实际 Dice 已过 0.95，但 24 个合格参考只匹配 16 个，匹配孔的体积误差 P95 为 39.49%。

**没有一个试件通过两组对照。** 从相对灰度换成精确灰度后，各件匹配 ID 和 P95 都没变，不能以两张掩膜的 Dice 不同当作逐孔提升。5 号相对严格阈值新增 #62，原有 9 孔的 P95 从 29.79% 降至 18.40%；相对灰度字典已经能做到。2 号严格阈值实际匹配了此前十二项目录均漏掉的 #28；精确字典则丢了 #26、#27、#28，另外找回四孔。选不同方法分别补这些已知对象会用到参考答案，不计作预测。

### 核对预测、上限和计量

- 预先固定规则；字典由原校准区共 4,718,592 个有标签中心得到，含 477,909 个精确组合和 20,295 个相对组合。未见过的组合依登记规则回退。发布模型计数、九张预测及文件摘要后，才读取此次评分所需的参考层。训练计数文件 `counts.npz` 与事后每件 `*-target-groups.npz` 分开，后者不得预测。
- CUDA 整数二分查表与 NumPy 对每个体素的三个判定一致；89 个邻点逐一求极值和独立最小/最大滤波一致。从源档跑两次得到的校准字典、九张掩膜、预测清单逐字节一致。
- 两路统计分别按灰度组合计数，以及按“组合+参考类别”联结后排序计数。每组最少错 `min(孔,材料)`；最大 Dice 则按组内孔比例排序、用整数交叉相乘比较全部前缀，再验证任何子集都不能得到更高分数。独立单测从 0 起算反复选择使分式收益为正的组，重新得到相同分数。最少错与最高 Dice 未必由同一判定规则取得。
- 每张预测以 8/37 层分块运行原生计量并和 SciPy 核对。两次独立进程从源档评分，18 份 CSV 和三份盲后计数表各自逐字节相同；四份 JSON 除原生运行秒数外相同。[完整证据与重放哈希](evidence/byte-window) · [登记](BYTE-WINDOW-TABLE.md) · [评分前的九张掩膜](https://github.com/EtherealBian/cone-fdk/tree/cb8ba8d7b95d051ac27713cf793bdd72a131fb0a/pores/evidence/byte-window) · [未变的正式验收](FINAL-GATE.md)。
